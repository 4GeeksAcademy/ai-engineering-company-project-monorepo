La idea en una frase: antes, los proveedores vivían en una hoja de cálculo que cada persona copiaba por su cuenta. Ahora viven en un solo sitio (una base de datos) al que todos acceden desde una página web, y ese sitio no deja entrar datos incorrectos.
1 · La idea

El problema y la solución

Antes Una hoja de cálculo

  • Varias versiones circulando por email y nadie sabía cuál era la buena.
  • Nadie sabía cuándo había cambiado el precio de un proveedor.
  • Podía entrar cualquier dato mal escrito: un país que no existe, un precio negativo.

Ahora Una API y una página web

  • Una única fuente de verdad: una base de datos.
  • Cada cambio de tarifa guarda la fecha y hora automáticamente.
  • Los datos incorrectos se rechazan antes de guardarse.

Piénsalo como un restaurante

Son dos programas que trabajan juntos. Uno es lo que ves, el otro es donde ocurre el trabajo.

FrontendEl comedorLa página web: la carta, las mesas. Lo que ve y toca Patricia.
⇄
BackendLa cocinaLa API: comprueba que el pedido tiene sentido y lo prepara. El jefe de cocina rechaza pedidos imposibles.
⇄
Base de datosLa despensaTinyDB: donde se guardan los datos. El cliente nunca entra aquí directamente.

El camarero que lleva los pedidos de un sitio a otro son las peticiones HTTP.

3 · Backend

La API: el cerebro que protege los datos

Una API es un programa que espera peticiones y responde. Cada petición tiene una dirección y un verbo, que es la acción.

GET

"Dame información"
GET /suppliers

POST

"Crea algo nuevo"
POST /suppliers

PATCH

"Cambia una parte"
PATCH /suppliers/1/rate

DELETE

"Borra" (solo activos)
DELETE /suppliers/3

Tres archivos, cada uno con un solo trabajo

models.py

El reglamento

Define qué datos son válidos. Si quieres cambiar una regla, solo tocas aquí.

routes/suppliers.py

La recepción

Recibe las peticiones, las deriva y traduce los errores a códigos HTTP.

database.py

El almacén

Arranca TinyDB, guarda y busca en la base de datos, un archivo db.json. seed.py la llena al empezar.

Los códigos de respuesta

200Todo bien
201Creado
204Hecho, sin nada que devolver
404No encontrado (un id que no existe)
409Conflicto (borrar un proveedor suspendido)
422Datos inválidos

El modelo: los campos de un proveedor

CampoQué esRegla
nameNombreObligatorio, no vacío
countryPaísSolo Spain o USA
categoriesTipo de servicioLista, mínimo una, solo las 9 permitidas
monthly_rateTarifa mensualNúmero mayor que 0
currencyMonedaEUR si es Spain, USD si es USA
statusEstadoSolo active o suspended
updated_atCuándo cambió la tarifaLo pone el servidor, nunca el cliente
contract_renewal_date, contact_email, notesExtrasOpcionales; el email, si existe, debe parecer un email

Pruébalo tú: el validador (Pydantic)

Es el "jefe de cocina" que rechaza pedidos imposibles. Cambia los valores y mira qué responde la API. Las reglas y mensajes son los reales.

El seeder: llenar la base de datos al empezar

Un seeder ("sembrador") carga los datos iniciales para que la demo nunca empiece vacía. Es idempotente: ejecutarlo dos veces no duplica nada.

Estado de la base:

La fecha de auditoría. El tech lead pidió saber cuándo cambia una tarifa. Por eso updated_at lo escribe el servidor con la hora actual cada vez que se cambia monthly_rate. Cambiar el estado o las notas no la toca.
4 · Frontend

La página web que ve Patricia

Está hecha con React (piezas reutilizables, como LEGO), TypeScript (un corrector que avisa de errores antes de ejecutar), Tailwind (estilos) y Vite (arranca la página y hace de proxy).

Piezas (componentes)

page.tsx ← la página: carga datos y coordina
  ├─ SupplierForm ← formulario "Nuevo proveedor"
  └─ SupplierRow ← una fila (se repite 15 veces)

El estado: la memoria de la página

La página recuerda la lista, el filtro elegido y los errores. Cuando algo de eso cambia, React redibuja solo lo que cambió. Por eso la tabla se actualiza sin recargar.

Una mini versión de la tabla (funciona de verdad)

Filtra por país y pulsa el botón de estado. Fíjate en que la página no se recarga y en cómo se distingue un proveedor suspendido.

ProveedorPaísCategoríaTarifa mensualEstado

Filtros

Filtran la lista que la página ya tiene en memoria. Es instantáneo. Con miles de proveedores se pediría el filtrado a la API, que ya lo sabe hacer.

Formulario

Valida en la página antes de enviar (nombre, tarifa > 0, categoría, email). Y si la API aun así rechaza, muestra su mensaje. La moneda se calcula sola según el país.

Tarifa y estado

La pantalla cambia después de que la API responde, para no mostrar algo que en realidad no se guardó.

¿Por qué validar en dos sitios? La página da respuesta inmediata a la persona. La API es la última defensa y nunca se puede saltar.
El proxy. La página vive en el puerto 5175 y la API en el 8000. Un navegador no deja que una página hable libremente con otro "domicilio". Vite hace de intermediario: recibe /api/suppliers y se lo pasa a la API.
5 · Decisiones

Lo que se decidió (y por qué)

1 Seguir la estructura que ya existía

En services/api/ ya había un módulo con router, schemas y service. Se copió esa organización. Un proyecto es más fácil de entender cuando todo se parece.

2 Usar exactamente los datos del encargo

Al principio se inventó una lista de ejemplo. Cuando llegó el archivo verdadero, se reescribió todo y se comprobó con un script que campos, categorías, estados y los 15 proveedores coinciden dato por dato. Cuando falta información, di qué supusiste.

3 No inventar un archivo que no existía

Se pidió leer CONTEXT-company.md. Se buscó en todo el repositorio y no existe. Se dijo claramente en lugar de aparentar haberlo leído.

4 Preguntar cuando la duda es real

"Parte desde cero" podía significar borrar código de otros hitos. Se preguntó antes de tocar nada. Una pregunta de 10 segundos es más barata que borrar algo por error.

5 Base de datos ligera: TinyDB

Lo pidió el tech lead: un archivo, sin servidor. Perfecto para empezar, pero no aguanta muchos usuarios escribiendo a la vez; por eso el README avisa y dice que luego se pasará a Postgres.

6 Estados en inglés

El encargo define active y suspended. Aunque la empresa sea española, se respetó el encargo: "activo" se rechaza.

7 Reorganizar para la entrega

La entrega pidió una estructura concreta. Como el código ya funcionaba, solo se movió con git mv (conservando el historial) y se adaptaron los imports. Las mismas 42 pruebas y las 28 comprobaciones de navegador pasan igual antes y después: reorganizar no es reescribir.

7 · Git y ramas

Cómo se ordenó el trabajo

Commit

Un "guardado" de tu proyecto, como en un videojuego, con un mensaje que explica qué cambió.

Rama

Una copia donde trabajas una idea sin estropear la versión oficial (main).

Pull Request

Una propuesta: "he hecho esto, ¿lo revisas y lo unes?". Muestra solo lo que cambió.

Todo el trabajo estaba en main. Para que sea fácil de entender se crearon 6 ramas encadenadas: cada una parte de la anterior y muestra una etapa (después se sumaron una rama de correcciones y otra con esta guía). En GitHub, abre la pestaña Pull requests y recórrelos del #3 al #10; en cada uno, Files changed enseña solo esa etapa.

base/pre-suppliers

El punto de partida, justo antes de este trabajo.

feature/suppliers-02-backoffice-pagePR #4

La página web: tabla, filtros, formulario, tarifa y estado (entonces en el backoffice).

Validación del formulario, contact_email y test en navegador.

docs/aprendiendo-con-la-iaPR #10

Esta guía.

delivery/suppliers-directoryEntrega

La estructura final que pide la entrega (models.py, database.py, routes/, seed.py y uis/application/app/suppliers/) más las 3 capturas del PR al repositorio original.

Honestidad. Las ramas se crearon después, apuntando a commits que ya estaban en main: por eso main no cambió ni se reescribió. Como los commits estaban entremezclados en el tiempo, el PR #7 junta backend con un arreglo de frontend.
Regla de aquí en adelante: cada cambio nuevo va en su propia rama y se propone con un Pull Request, sin tocar main directamente. Nunca se usó git push --force.

Los tests: la lista de revisión del piloto

Backend · 42 pruebas

Comprueban que el modelo tiene los campos del encargo, que un estado o tarifa inválidos dan 422 sin llegar a la base, que el cliente no puede enviar updated_at, y los 201, 404, 409 y 204 de cada endpoint. Cada test usa una base temporal.

Navegador · 28 comprobaciones

Abre un navegador de verdad (Chromium y Firefox, con Playwright) y usa la página como una persona: filtra, rellena mal el formulario, cambia una tarifa y un estado, y comprueba que también quedó guardado en el servidor.

8 · Comandos

Ver el proyecto funcionando

Necesitas dos terminales en VS Code (menú Terminal → Nueva terminal): una para la API y otra para la página.

¿Dónde está la raíz del repositorio? Es la carpeta principal del proyecto: /workspaces/ai-engineering-company-project-monorepo-INES. Si tu terminal no está ahí, escribe el comando de abajo.
cd /workspaces/ai-engineering-company-project-monorepo-INES

Terminal 1 · la API

cd services/api uv run uvicorn main:app --reload --port 8000

Carga sola los 15 proveedores. Lista en bruto: localhost:8000/suppliers. Documentación interactiva, donde pruebas cada acción con un botón: localhost:8000/docs.

Terminal 2 · la página (desde la raíz)

npm run dev:application

Abre localhost:5175/suppliers. En Codespaces, abre el puerto 5175 desde la pestaña Puertos.

Volver a los datos iniciales (antes de una demo)

cd services/api uv run seed --reset

Ejecutar las pruebas del backend

cd services/api uv run --with pytest --with httpx pytest -q
Si uv run seed dice "Failed to spawn", estás en la carpeta equivocada: uv busca el pyproject.toml en la carpeta donde estás. Ejecútalo dentro de services/api, o desde la raíz con uv run --project services/api seed.

Las palabras difíciles, explicadas

Consejos para seguir aprendiendo: (1) Abre models.py, cambia gt=0 a gt=10 y mira qué test falla; luego deshazlo. (2) Abre localhost:8000/docs y pulsa "Try it out" en cada endpoint. (3) Rompe cosas a propósito: los errores enseñan más que los aciertos. (4) Lee un test para entender una función. (5) Pregunta siempre el "porqué".
